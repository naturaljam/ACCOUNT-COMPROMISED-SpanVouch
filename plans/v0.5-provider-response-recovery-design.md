# SpanVouch v0.5 Provider Response Recovery Design

**Status:** Approved approach A, pending written-spec review

**Incident:** The authorized DeepSeek candidate run stopped after 19 of 216
published candidates. The twentieth provider response was returned and therefore
billable, but the generic artifact classifier rejected its raw JSON string before
the diagnosis schema could interpret it. The response was not persisted, the
reservation was released, and the CLI could not resume into the existing output
repository.

## Goal

Make live Phase 5 execution safely recoverable without weakening credential
handling or changing the frozen experiment manifest. The repaired path must:

- normalize provider content through its consumer schema before caching it;
- persist no raw rejected content or raw provider identifiers;
- account for every provider response whose usage is available, including content
  rejected after the call;
- distinguish accepted, rejected, and conservative reconciled charges;
- resume only after fully verifying every existing candidate;
- retain the same request identity, candidate manifest, prompt bytes, model,
  decoding configuration, and experimental conditions.

## Root Cause

`GuardedProvider` currently applies `require_safe_artifact_content` to the complete
serialized `response.content` string. The generic classifier treats any long,
high-entropy lexical atom as secret-like. A diagnosis JSON document can satisfy the
Pydantic draft schema and still contain such an atom in legitimate model-derived
text. This was reproduced locally with a schema-valid diagnosis draft.

The same method releases its budget reservation for every exception. Once the
delegate has returned a valid `ProviderResponse`, the provider call has already
happened and may be billed. Releasing that reservation without a charge makes the
global ledger incomplete.

Finally, `run_phase5_candidates` rejects any existing output directory, even though
candidate cells are independently content-addressed and published with no-replace
semantics. This prevents a verified restart after a partial run.

## Architecture

### 1. Schema-aware content policy seam

Add a small `ProviderResponseContentPolicy` interface at the `GuardedProvider`
response seam:

```text
normalize(raw_content) -> NormalizedProviderContent

NormalizedProviderContent:
  content              canonical consumer-facing JSON
  disposition          accepted | normalized_invalid
```

Two adapters make the seam real:

- a diagnosis adapter validates the diagnosis draft shape;
- a semantic-verifier adapter validates the semantic draft shape.

Both adapters first apply non-bypassable credential signatures to the raw string.
They never return the raw string. A valid document is re-serialized as canonical
JSON from the validated model. Invalid, credential-like, or structurally unsafe
content becomes a fixed canonical invalid document (`{}`), which the existing
diagnoser or semantic verifier deterministically maps to its established
invalid-output result. This preserves failure evidence instead of crashing or
silently retrying until a favorable answer appears.

The policy result, not the raw provider string, is scanned by the artifact
classifier and stored in the provider cache. The audit record gains a content
disposition so normalized invalid outputs remain visible in experiment evidence.

### 2. Returned-response accounting

Extend provider charges with a disposition:

```text
accepted | rejected | rejected_estimate
```

Existing rows migrate to `accepted`. `BudgetLedger.commit` continues to close an
accepted request and prevents rebilling when its cache entry is missing.

Add a rejected settlement operation that atomically:

1. records the provider charge using validated usage;
2. closes the reservation as rejected;
3. releases the global semantic request claim so a later authorized retry is
   possible;
4. records an overrun stop event if actual usage exceeds the reservation.

Rejected charges count toward monthly and pilot totals but do not satisfy
`committed_request_cost`, because they produced no reusable cache result.

For the already released twentieth request, add a narrowly validated reconciliation
operation. It may charge only an existing released reservation with no prior charge,
and the amount may not exceed that reservation. The repair will record the frozen
upper-bound amount `0.010542 CNY` as `rejected_estimate`; it will not invent token
usage or claim this is the exact provider bill.

### 3. Verified candidate resume

Add an explicit `--resume` flag. Without it, the current no-existing-output behavior
remains unchanged.

On resume, every existing cell is loaded through the candidate repository's secure
directory-tree reader and checked for:

- content-addressed filename and canonical bytes;
- exact corpus cell, corpus manifest, record hash, and trace hash;
- exact generation configuration, provider, model, and prompt reconstruction;
- absence of raw request IDs and unsafe persisted content.

Only verified cells are skipped. Missing cells execute in original manifest order.
An invalid, extra, or mismatched cell fails before a new provider call. The partial
19-candidate repository remains immutable and is reused as-is.

### 4. Manifest and authorization invariants

The candidate-generation manifest remains
`30224fda50910897f388773bc7e2bd0328ac023dfd6a990c821120c4c4652517`.
Content normalization and resume mechanics are execution controls, not experiment
inputs. They do not change prompts, corpus cells, model identity, decoding settings,
or candidate schema.

No paid call occurs during implementation or verification. After all local gates
pass, the resumed run requires a new explicit authorization for the 197 missing
candidates because completing the failed twentieth cell raises the lifetime provider
call count for this manifest from 216 to at most 217.

## Failure Behavior

- Missing content policy: reject before provider I/O.
- Explicit credential signature or invalid provider JSON: normalize to canonical
  invalid content, record an accepted charge for that reusable normalized result,
  cache only normalized content, and preserve an invalid-output experimental result.
- Failure before any `ProviderResponse` exists: release reservation with no charge.
- Failure after validated usage exists but before reusable cache publication: record
  a rejected charge and allow a separately authorized retry.
- Existing candidate tampering or provenance drift: stop before provider I/O.
- Reconciliation target mismatch, duplicate charge, or amount above reservation:
  fail closed without changing the ledger.

## Testing

Implementation is test-first and covers:

1. a schema-valid diagnosis containing a long high-entropy identifier is
   canonicalized rather than rejected as a secret;
2. explicit authorization, bearer, token-prefix, JWT, and private-key signatures
   never enter normalized content or cache;
3. invalid diagnosis and semantic JSON become their existing invalid-output results,
   are charged once, and reuse the normalized cache result without a second call;
4. an unexpected policy or persistence failure after validated usage creates a
   rejected charge, no reusable cache entry, no active reservation, and permits a
   later authorized retry;
5. transport failures before a response remain uncharged;
6. existing ledgers migrate accepted dispositions without total drift;
7. the released twentieth reservation reconciles once at or below its reserved
   upper bound and cannot be reconciled twice;
8. resume skips 19 verified cells, rejects tampering and unknown cells before I/O,
   and calls the provider only for missing cells;
9. secrets and raw response/request IDs are absent from candidates, cache, ledger,
   audits, and error text;
10. focused tests, the complete pytest suite, Ruff, mypy, and wheel build pass before
    renewed paid authorization is requested.

## Non-Goals

- No Qwen, B0-B5 matrix, formal run, paper update, remote push, tag, or release.
- No change to the IVAD protocol, corpus, prompts, candidate manifest, or pricing.
- No persistence or reconstruction of the rejected twentieth raw response.
- No automatic paid retry and no relaxation of explicit credential signatures.
