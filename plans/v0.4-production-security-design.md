# SpanVouch v0.4.0 Production Security Design

**Status:** Approved design for specification review

**Release theme:** Production Security and Audit

**Baseline:** SpanVouch v0.3.0, commit `d3ccecea89c9c0bad3df0c8d8c3c1153ad9b625d`

**Content type:** Conceptual design specification

This specification defines the production-security slice that makes SpanVouch safe to operate as a self-hosted service while preserving its deterministic evidence workflow.

## Goal

Make the existing durable trace and human-review workflow safe to operate as a single-organization self-hosted service. v0.4.0 adds project isolation, mandatory authentication, role-based authorization, signed audit exports, and a complete management workflow without changing the deterministic diagnosis core.

## Scope

The release is one vertical production-security slice:

- project-scoped data ownership for traces, diagnoses, reviews, and audit exports;
- built-in API keys with project roles, rotation, revocation, and expiry;
- mandatory authentication for every endpoint except health and readiness probes;
- management API and CLI using one authorization policy implementation;
- append-only per-project SHA-256 audit chains;
- Ed25519-signed audit checkpoints and offline-verifiable export bundles;
- a pinned `cryptography` runtime dependency for signing and independent verification;
- transactional database migration from schema v3 to schema v4;
- backup/restore and container restart acceptance gates for security state and audit history.

The release remains self-hosted and provider-neutral. Existing rules-based diagnosis, offline verification, review state transitions, idempotency, and optimistic concurrency remain unchanged except for project authorization at their boundaries.

## Non-Goals

The following are deliberately outside v0.4.0:

- OIDC, SAML, external identity providers, or a web administration console;
- multi-organization SaaS billing, quotas, or account provisioning;
- PostgreSQL or distributed database support;
- external WORM storage, hosted logging, or vendor-specific audit services;
- a general metrics, alerting, or incident-management platform;
- live provider experiments or changes to paper claims.

## Decisions

### Deployment model

The service targets one organization with multiple isolated projects. The schema and authorization interfaces must preserve a future path to multi-tenant deployment, but v0.4.0 does not implement organization billing or cross-organization identity.

### Authentication

Clients send `Authorization: Bearer svk_<key-id>_<secret>`. Keys are displayed once at creation and are stored only as a `hashlib.scrypt` digest with a 16-byte random salt, non-secret prefix, optional project, roles, status, timestamps, and optional expiry. The digest uses `n=16384`, `r=8`, `p=1`, and a 32-byte output, then compares with a constant-time operation. Revocation and rotation invalidate the old credential immediately.

The `/health` and `/ready` probes remain unauthenticated. All other HTTP routes require a valid, non-expired, non-revoked key. A first-start bootstrap flow creates one administrator key, displays it once, and records the bootstrap event. The bootstrap credential cannot be recreated by restarting the service.

An `admin` key is system-scoped and has no `project_id`. Every non-admin key belongs to exactly one project. A system administrator selects a target project through `X-SpanVouch-Project`; the server validates that header only after authenticating the administrator, then records the selected project in the audit event. A non-admin request cannot select or override its key's project.

### Roles

The initial role set is deliberately fixed:

| Role | Allowed operations |
| --- | --- |
| `admin` | Manage projects, keys, role assignments, audit exports, and all project data |
| `operator` | Ingest traces, run diagnosis, create/resume review work, and read operational state |
| `reviewer` | Read trace/diagnosis/review evidence and record human review decisions |
| `viewer` | Read project-scoped traces, diagnoses, reviews, and audit summaries |

Authorization is evaluated from a typed `Principal` at the application boundary and enforced again by project-scoped repository queries. No route may infer project ownership from an untrusted request field.

### Project isolation

`project_id` is a required persisted field on every trace, diagnosis, review case, immutable event, and audit export. Resource lookup uses both `project_id` and the resource identifier. A resource belonging to another project is reported as `404` to avoid cross-project enumeration; an authenticated principal lacking the required role receives `403` for an otherwise visible project operation.

Existing v0.3 data is migrated into a deterministic `default` project in one transaction. The migration preserves identifiers, review versions, event order, idempotency records, and existing integrity hashes. A failed migration leaves the original database readable and does not partially expose v4 tables.

### Audit integrity

Every mutating operation records an audit event in the caller's project. Each event contains:

- a monotonically increasing project-local sequence;
- canonical JSON payload and its SHA-256 hash;
- the previous event hash;
- actor principal, role, action, resource type, resource identifier, and result;
- UTC timestamp and request correlation identifier.

An audit checkpoint contains the project identifier, covered sequence range, terminal event hash, canonical manifest hash, and an Ed25519 signature. The signing private key is loaded from the deployment-only `SPANVOUCH_AUDIT_SIGNING_KEY_PATH` file and is never returned by the API. The corresponding public key is included in every export.

### Export contract

Online access provides paginated audit events and checkpoint metadata. A formal export is an existing `ArtifactManifest` bundle containing:

```text
manifest.json
events.jsonl
checkpoints.json
public-key.pem
README.md
```

The manifest records each file hash, project identity, sequence range, terminal chain hash, signing key fingerprint, and export command. An offline verifier using the pinned `cryptography` dependency must validate file hashes, event continuity, checkpoint signatures, and manifest consistency without database access or provider credentials.

## Interface Shape

The management API is the source of truth; the CLI is a thin client over the same HTTP contracts and policy decisions.

### Management endpoints

```text
POST /v1/admin/projects
GET  /v1/admin/projects
POST /v1/admin/projects/{project_id}/api-keys
POST /v1/admin/api-keys/{key_id}/rotate
POST /v1/admin/api-keys/{key_id}/revoke
GET  /v1/admin/audit-exports
POST /v1/admin/projects/{project_id}/audit-exports
GET  /v1/admin/audit-exports/{export_id}
```

The existing trace, diagnosis, review, health, and readiness routes remain at their current paths. Their handlers receive a validated `Principal` and project context before invoking application services.

### CLI commands

```text
spanvouch admin project create
spanvouch admin project list
spanvouch admin key create
spanvouch admin key rotate
spanvouch admin key revoke
spanvouch admin audit export
spanvouch admin audit verify
```

Secrets must never be accepted as command-line arguments, written to normal logs, or included in error payloads. Interactive output prints a newly created key exactly once; non-interactive output supports an explicitly requested secure file descriptor or environment handoff.

## Module Boundaries

The implementation should add focused modules rather than place authorization branches throughout existing storage code:

- `src/spanvouch/security/identity.py`: principal, API key hashing, bootstrap, rotation, and revocation;
- `src/spanvouch/security/policy.py`: role-to-capability policy and authorization decisions;
- `src/spanvouch/projects/`: project models and project-scoped service operations;
- `src/spanvouch/audit/chain.py`: canonical event chaining and checkpoint construction;
- `src/spanvouch/audit/export.py`: ArtifactManifest export and offline verification;
- `src/spanvouch/api/routes/admin.py`: management endpoints only;
- `src/spanvouch/cli/admin.py`: management CLI client only;
- existing storage/application modules: receive typed project and principal inputs, with no duplicated role logic.

The exact filenames may be adjusted during the implementation plan if an existing package boundary is a better fit, but the responsibilities and dependency direction are fixed by this design.

## Testing and Acceptance

The feature is implemented test-first. The acceptance matrix must include:

1. anonymous requests to protected routes return `401`, while health and readiness remain public;
2. each role is allowed and denied exactly according to the role matrix;
3. cross-project reads and writes cannot discover or mutate another project's resources;
4. keys are hashed at rest, shown once, rotate correctly, revoke immediately, and expire correctly;
5. bootstrap initialization is one-shot and restart-safe;
6. every mutating API and management operation emits a complete audit event;
7. concurrent audit writers produce one contiguous chain without duplicate sequence numbers;
8. tampering with any event, checkpoint, public key, or exported file is detected offline;
9. v3-to-v4 migration preserves all existing trace, diagnosis, review, idempotency, and event state;
10. container replacement and backup restore preserve project permissions and audit history;
11. existing deterministic and provider-neutral tests remain green without provider credentials;
12. Linux and Windows CI continue to pass the current `92` percent coverage floor, wheel build, Compose validation, offline acceptance, and container smoke gates.

## Release Criteria

v0.4.0 is releasable only when the full local and CI gates pass, the migration has a tested rollback path, the signed export has an independent verification command, and the README examples demonstrate the secure bootstrap-to-audit workflow. No remote push or GitHub release is implied by this design document; publishing requires a separate explicit approval after implementation verification.

## Follow-up Versions

OIDC integration, multi-organization tenancy, external immutable storage, richer observability, and provider-backed production experiments remain candidates for v0.5 or later. They must not be pulled into v0.4.0 merely because their interfaces are anticipated here.
